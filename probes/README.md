# Probes

One-off measurements. A probe answers a question about the browser, the fixture or a
finished run; it is not part of the measurement path, and nothing in `core/` imports
from here. They live in the repo rather than in a scratch directory because each one
is the evidence behind a claim in `PROJECT-LOG.md`, and a claim whose measurement
cannot be re-run is an anecdote.

| Probe | Question it answers | Last finding |
|---|---|---|
| `launch-probe.mjs` | Can the harness stand up its own flagged Chrome, and does that browser see WebMCP? | Yes on `152.0.7977.65`, cold profile, `--headless=new` |
| `fixture-manifest.mjs` | What did a fixture page *try* to register, and what did the browser hand back? | `registerTool` throws `"Invalid tool name"` for a name with a space; dotted names register |
| `webmcp-domain.mjs` | What does the CDP `WebMCP` domain expose, and does the browser's tool list agree with the page's? | No command lists tools — only `toolsAdded`/`toolsRemoved` events. The two views agreed at 7, 71, 187, 307 and 507 tools, and across an iframe |
| `chatgpt-browser-probe.mjs` | Can the ChatGPT desktop app's built-in browser be driven over CDP at all? (item 9) | **Yes.** Attach works, `--enable-blink-features=WebMCPTesting` at launch wakes `modelContext` on **both** `document` and `navigator`, and all 7 Airlock tools are readable. The WebMCP CDP domain exists but is not advertised in `/json/protocol` |
| `binary-webmcp-strings.mjs` | Which WebMCP feature/flag strings did a given browser binary compile in? | On the Codex/ChatGPT Chromium 151: `enable-webmcp-testing`, `WebMCPTesting`, `WebMCP`, `devtools-webmcp-support`, the CDP domain methods, and blink's `ModelContext` class — the machinery is all present; discovery needed the string dump to name the right switch |
| `invoke-paths.mjs` | Do the page API and the browser's own domain execute a tool the same way? | **Both work, identical payloads, different shapes.** Page: `executeTool(toolObject, jsonString)`, awaitable. Domain: `WebMCP.invokeTool({frameId, toolName, input: <object>})` returns `{invocationId}` and the result arrives **asynchronously** as `WebMCP.toolResponded {invocationId, status:"Completed", output}` — an object, not a string. Same on Chromium 151 (ChatGPT) and Chrome 152 |
| `cohort-snapshot.mjs` | What did a whole cohort of pages actually register, on the one day they were all live? | Staged and dry-run 2026-09-01 against 4 targets (3 after alias collapsing): 7 tools on the reference page, 0 on a live page without WebMCP, 404 recorded as dead. Writes `snapshot.jsonl` (full manifests, local) and `publishable.json` (shape only) per dated directory. Rules live in `core/cohort.mjs` **with tests**, because the capture cannot be repeated |
| `gallery-harvest.mjs` | Which project URLs are in a Devpost gallery, and which of a submission's links is the thing to measure? | Rehearsed 2026-09-01 against three published galleries and three real project pages. **Devpost answers headless Chrome with 202 and an empty body — run headed.** Cards are `a.link-to-software`; the pager names the last page (`?page=26` on a 26-page gallery), so the walk stops on the pager rather than on "nothing new"; submission links live in `.app-links` and **only** there. Refuses rather than guesses: unpublished gallery, no selector match, or a pager longer than `--max-pages` all exit 2 |
| `mode-b-session.mjs` | Does the real ChatGPT agent invoke a page's tools, and can the browser record it? | **Unanswered, because the design's surface was wrong.** Two prompts to the signed-in agent produced no event and no page change: the app's own context reads `Chrome tabs: The user has the Chrome extension side panel open…`, so the agent sees the **user's ordinary Chrome through an extension**, not tabs this project opens in the app's browser. Classifies on four signals (event, page fingerprint, delivery confirmation, agent page-context) so a silence can never be published as a null result |
| `frame-scope.mjs` | Whose tools land in whose manifest, across a frame boundary? | **Three answers, and one disagreement.** Same-origin: one shared manifest, both frames see all 4 tools. Cross-origin with no `allow`: `document.modelContext` exists but throws *"Access to the feature `tools` is disallowed by permissions policy"* — so WebMCP is gated by a Permissions Policy feature named **`tools`**, not delegated by default. Cross-origin with `allow="tools"`: the embed registers, **the browser reports all 4 across 2 frames, and no script-visible surface returns the union** — the host sees 3, the embed sees 1. The only page-view/browser-view divergence this project has found. Backs [webmcp#227](https://github.com/webmachinelearning/webmcp/issues/227#issuecomment-5499568493) |
| `render-scorecards.mjs` | What would a private scorecard for one captured project say? | Writes one Markdown file per project from a snapshot's `snapshot.jsonl`, worst-first, using `report/scorecard.mjs` (8 tests). **Sends nothing** — delivery is a gated decision in the log, not a flag here. Skips pages that registered no tools, because "you have no tools" is not feedback. Reference page renders 0E/0W across 7 tools; the delegated-embed capture renders 3W plus the divergence section |
| `compare-arms.mjs` | How do several finished runs compare per tool? | Prints rates with intervals, between-session σ, failure mix and the phrasing gradient |
| `utterance-floor.mjs` | Which utterances fail even on a well-described page? | One: `sum_by_category-12`, 12 of 13 (see `fixtures/README.md`) |
| `expr-*.js` | Raw evaluation expressions for hand-driven CDP sessions | Kept as the smallest reproductions of each browser fact |

## Next steps that land here

1. **`budget` and `compare` are probes pretending to be commands.** `docs/concept.md` sketches `webmcp-gauge budget <url>` and `webmcp-gauge compare base.json head.json`; today those are `webmcp-domain.mjs --flood` and `compare-arms.mjs`. Promote them only when their shape is settled — what a baseline is, and what counts as a regression, is not decided yet, and a CLI surface is much harder to change than a probe.
2. **The budget question is only answered for one client.** `webmcp-domain.mjs` found no ceiling on Chrome 152 up to 507 tools, which contradicts the 296-tool field report. Edge and the ChatGPT in-app browser are unmeasured, and they are where a budget would actually bite. The ChatGPT browser is now reachable for that measurement — `chatgpt-browser-probe.mjs` documents the launch recipe (MSIX path + `--remote-debugging-port` + `--enable-blink-features=WebMCPTesting`) — but the budget run has not been done.
3. ~~**`WebMCP.invokeTool` is never exercised.**~~ ✅ **Done 2026-09-01** — `invoke-paths.mjs`. Both paths execute and return the same payload, but the shapes differ and the domain path is asynchronous, so an adapter cannot treat them as interchangeable. The parameter shape is documented nowhere this project can cite; it was walked out of the CDP deserializer's own errors, one mandatory field at a time (`frameId`, then `input` as an object, then `toolName`). Two things this unlocks: the domain path is what a real client uses, and `toolInvoked` carrying `{toolName, input}` is the mechanism the sampled Mode B design records with — see `docs/concept.md`, "Mode B, as designed on 2026-09-01".
4. **Nothing here is tested**, on purpose — a probe is a measurement, not a component. If a probe's logic ever becomes load-bearing for a published number, it moves into `core/` or `browser/` and gets tests, as the manifest reader and the browser-side tool view both did.
