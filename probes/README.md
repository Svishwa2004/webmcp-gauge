# Probes

One-off measurements. A probe answers a question about the browser, the fixture or a
finished run; it is not part of the measurement path, and nothing in `core/` imports
from here. They live in the repo rather than in a scratch directory because each one
is the evidence behind a claim in `PROJECT-LOG.md`, and a claim whose measurement
cannot be re-run is an anecdote.

**Options.** Every probe here shares `bin/`'s parser (`core/args.mjs`, since
2026-09-03), so `--name value` and `--name=value` are the same thing everywhere and
an unknown or valueless option is an error rather than a silently ignored default.
That fix has a cost story: for one day the probes read `--name=value` only, and
`--serve fixtures/gallery` therefore walked the **live** gallery while claiming to
walk a local fixture.

| `launch-probe.mjs` | Can the harness stand up its own flagged Chrome, and does that browser see WebMCP? | Yes on `152.0.7977.65`, cold profile, `--headless=new`. **Also Edge `153.0.4234.13` (2026-09-03) via `WEBMCP_GAUGE_CHROME=…\msedge.exe`** — the launcher always took a path, so one env var aims the whole harness at any Chromium build, and the Chrome labs recipe works on Edge unchanged |
| `fixture-manifest.mjs` | What did a fixture page *try* to register, and what did the browser hand back? | `registerTool` throws `"Invalid tool name"` for a name with a space; dotted names register |
| `webmcp-domain.mjs` | What does the CDP `WebMCP` domain expose, and does the browser's tool list agree with the page's? | No command lists tools — only `toolsAdded`/`toolsRemoved` events. The two views agreed at 7, 71, 187, 307 and 507 tools, and across an iframe. **`--port=` added 2026-09-03** so the same questions can be put to a browser the harness cannot launch: on the ChatGPT build's Chromium `152.0.7977.64` the views agree at 7/7, 507/507 and 8/8 across 2 frames, and the domain is advertised in `/json/protocol` with a surface identical to Chrome 152 |
| `chatgpt-browser-probe.mjs` | Can the ChatGPT desktop app's built-in browser be driven over CDP at all? (item 9) | **Yes, on two builds.** Attach works, `--enable-blink-features=WebMCPTesting` at launch wakes `modelContext`, and all 7 Airlock tools are readable. On Chromium `151.0.7922.174` (2026-09-01) `modelContext` sat on **both** `document` and `navigator`; on `152.0.7977.64` (2026-09-03) only on `document`, so that was a version behaviour rather than a fork behaviour. ❌ **Correction 2026-09-03:** this probe reported the `WebMCP` CDP domain as absent from `/json/protocol` because it tested `d.name` where CDP keys entries `d.domain` — always false, on every build. The domain **is** advertised; the read is fixed and now reports the domain count beside the verdict |
| `binary-webmcp-strings.mjs` | Which WebMCP feature/flag strings did a given browser binary compile in? | On the Codex/ChatGPT Chromium 151: `enable-webmcp-testing`, `WebMCPTesting`, `WebMCP`, `devtools-webmcp-support`, the CDP domain methods, and blink's `ModelContext` class — the machinery is all present; discovery needed the string dump to name the right switch |
| `invoke-paths.mjs` | Do the page API and the browser's own domain execute a tool the same way? | **Both work, identical payloads, different shapes.** Page: `executeTool(toolObject, jsonString)`, awaitable. Domain: `WebMCP.invokeTool({frameId, toolName, input: <object>})` returns `{invocationId}` and the result arrives **asynchronously** as `WebMCP.toolResponded {invocationId, status:"Completed", output}` — an object, not a string. Identical on all three builds measured: Chrome `152.0.7977.65`, and the ChatGPT app at Chromium `151.0.7922.174` and `152.0.7977.64` |
| `cohort-snapshot.mjs` | What did a whole cohort of pages actually register, on the one day they were all live? | Staged and dry-run 2026-09-01 against 4 targets (3 after alias collapsing): 7 tools on the reference page, 0 on a live page without WebMCP, 404 recorded as dead. Writes `snapshot.jsonl` (full manifests, local) and `publishable.json` (shape only) per dated directory. Rules live in `core/cohort.mjs` **with tests**, because the capture cannot be repeated. **Its seam with the harvester is tested since 2026-09-03** (`core/capture-seam.test.mjs`): a harvest's targets are consumed without translation, a submission with no demo link never arrives, and two submissions sharing one deployment are two harvest rows and **one** capture — so a census must not report projects and captures as the same number |
| `gallery-harvest.mjs` | Which project URLs are in a Devpost gallery, and which of a submission's links is the thing to measure? | Rehearsed 2026-09-01 against three published galleries and three real project pages. **Devpost answers headless Chrome with 202 and an empty body — run headed.** Cards are `a.link-to-software`; the pager names the last page (`?page=26` on a 26-page gallery), so the walk stops on the pager rather than on "nothing new"; submission links live in `.app-links` and **only** there. Refuses rather than guesses: unpublished gallery, no selector match, or a pager longer than `--max-pages` all exit 2. `--serve=fixtures/gallery --probe` walks a local fixture — pager, cascade, dedupe — with no third-party traffic |
| `gallery-status.mjs` | Is the gallery published yet, and what does the host's own schedule say about when it should be? | **Not published at 2026-09-05 07:03 UTC / 12:33 local**, ~23 h after submissions closed — which falsified item 12's date lock ("the gallery opens on the 4th" was our inference, not the host's statement). The host's `/details/dates` says: submissions closed **Sep 04 1:30 PM** GMT+5:30 — the log had recorded 01:30, a PM read as AM — judging runs to **Sep 22 5:30 AM**, winners announced **Sep 24 2:30 AM**. So the gallery most plausibly opens at the far end of judging, and this probe exists so three weeks of waiting costs one command instead of running the capture-day script idly. Three verdicts like `remote-visibility.mjs`: 0 published, 1 definitively not, 2 cannot answer (robots, a non-200, headless's 202, or markup carrying neither answer) |
| `name-proxy-rule.mjs` | Does item 22's option (b) work, and what does it cost? | **It reproduced every measured arm, so it was adopted** (2026-09-05). `description/indistinguishable-pair` — two tools whose names are lexically close **and** neither description echoing the tokens of its own name — fires on all five ladder rungs (48.3% to 83.3%) and stays silent on every manifest that cost nothing: `clean` 95.0%, `ablate-competitor-vague` 95.0%, `ablate-desc-degraded` 93.3%, `ablate-thin` 100.0%, plus both published single-defect arms. It also catches a pair nobody designed it for, the dotted `top.expenses.v2` beside `top_expenses`, and correctly ignores `ablate-schema`, which loses 46.7 points by a different mechanism that its own rule already flags. **The rule now ships in `core\lint.mjs` as a warning** — not an error, because 13 manifests from one fixture family is not a false-positive rate — and this probe is what re-measures it: it imports the shipped rule and exits 1 if the rule ever stops reproducing the arms |
| `mode-b-session.mjs` | Does the real ChatGPT agent invoke a page's tools, and can the browser record it? | **Unanswered, because the design's surface was wrong.** Two prompts to the signed-in agent produced no event and no page change: the app's own context reads `Chrome tabs: The user has the Chrome extension side panel open…`, so the agent sees the **user's ordinary Chrome through an extension**, not tabs this project opens in the app's browser. Classifies on four signals (event, page fingerprint, delivery confirmation, agent page-context) so a silence can never be published as a null result |
| `frame-scope.mjs` | Whose tools land in whose manifest, across a frame boundary? | **Three answers, and one disagreement.** Same-origin: one shared manifest, both frames see all 4 tools. Cross-origin with no `allow`: `document.modelContext` exists but throws *"Access to the feature `tools` is disallowed by permissions policy"* — so WebMCP is gated by a Permissions Policy feature named **`tools`**, not delegated by default. Cross-origin with `allow="tools"`: the embed registers, **the browser reports all 4 across 2 frames, and no script-visible surface returns the union** — the host sees 3, the embed sees 1. The only page-view/browser-view divergence this project has found. Backs [webmcp#227](https://github.com/webmachinelearning/webmcp/issues/227#issuecomment-5499568493). Reproduced on Edge 153 as well as Chrome 152 — 09-03 |
| `site-scope.mjs` | Do those findings survive a **site** boundary, and are `localhost` and `127.0.0.1` even different sites? | **Yes they are different sites** — the cross-site child gets its own `type:"iframe"` target while a cross-origin (different-port) child gets none — so the matrix's cross-site rows needed no real domains. With `allow="tools"`, the embed registers and sees its own tool through that target, but the **host session's** browser view holds only the host's 3 tools across 1 frameId: the union exists only in the child's target. Without `allow`, the Permissions Policy gate throws in the child even cross-site. ⚠️ Two of this probe's own first-version reads were wrong and are kept as comments in the file: `/json/list` matching by URL substring hit the host page (the query string carries the widget URL), and CDP's frame tree hangs `childFrames` off the tree *node*, not the frame object |
| `browser-scope.mjs` | Can a **browser-level** CDP client see the cross-site embed a host-attached one cannot? | **Yes, and it closes the matrix row that asked** (2026-09-05). Attached at the browser endpoint with `Target.setAutoAttach` armed **recursively** — on every session as it attaches — the client reaches the OOPIF and sees **4 tools across 2 target sessions** including `widget_ping`, while the host-attached session and every page surface see 3. So *no page can enumerate what an agent can call on it* stands; *no client can* was never true. ⚠️ **The first run armed auto-attach only on the browser session, saw 3 tools, and would have published the opposite answer** — browser-level auto-attach alone does not reach an out-of-process iframe. That near-miss is why the probe now prints the OOPIF session count beside the verdict and refuses (exit 2) when none attached. Both views are measured in one run against one navigation, so the contrast cannot be two page loads |
| `cohort-rehearsal.mjs` | Does the **real cohort capture** see the cross-site union, on the shape that breaks a host-attached watch? | **PASS 2026-09-25** — item 23's rehearsal bar, run through the actual `cohort-snapshot.mjs` rather than a copy of its logic: the `spec-227` fixture pair served on the two loopback names Chrome treats as different sites, the delegating page captured, and the *record the capture writes* checked line by line — page view 3, agent view **4 including `widget_ping`**, ≥1 OOPIF session in the record's new `webmcp.browserView` metadata, widget attributed `sameOrigin: false`. Exits 2 (cannot answer) rather than 1 when no OOPIF session ever attached, the same guard `browser-scope.mjs` added after its own near-miss — a capture that measured auto-attach must not publish as the browser's view |
| `render-scorecards.mjs` | What would a private scorecard for one captured project say? | Writes one Markdown file per project from a snapshot's `snapshot.jsonl`, worst-first, using `report/scorecard.mjs` (8 tests). **Sends nothing** — delivery is a gated decision in the log, not a flag here. Skips pages that registered no tools, because "you have no tools" is not feedback. Reference page renders 0E/0W across 7 tools; the delegated-embed capture renders 3W plus the divergence section |
| `compare-arms.mjs` | How do several finished runs compare per tool? | Prints rates with intervals, between-session σ, failure mix and the phrasing gradient |
| `remote-visibility.mjs` | Is the remote still invisible to a stranger, as the publishing policy requires? | Two independent signals — an unauthenticated GitHub API read, and an anonymous `ls-remote` with the credential helper disabled — and **three** verdicts, because `indeterminate` has to be one of them. Exit 0 private on both signals, 1 a definitive public answer, 2 cannot answer. Rules live in `core/visibility.mjs` **with 19 tests**, because this one gates a push: a check whose failure path cannot tell *no answer* from *the answer I expected* is not a check. All three exits verified live 2026-09-03 — `--url=` a known-public repo → 1, `--timeout=1` → 2, this remote → 0 |

## Next steps that land here

1. **`budget` and `compare` are probes pretending to be commands.** `docs/concept.md` sketches `webmcp-gauge budget <url>` and `webmcp-gauge compare base.json head.json`; today those are `webmcp-domain.mjs --flood` and `compare-arms.mjs`. Promote them only when their shape is settled — what a baseline is, and what counts as a regression, is not decided yet, and a CLI surface is much harder to change than a probe.
2. ~~**The budget question is only answered for one client.**~~ ✅ **Three engines, same answer — 2026-09-03.** `webmcp-domain.mjs 0,507` on Chrome and the same command under `WEBMCP_GAUGE_CHROME` on Edge, plus `--port=9333` against the ChatGPT desktop build: **507 of 507 registered, listed and surfaced, 0 rejected, on all three.** The 296-tool field report reproduces on none of them, and the `budget/headroom` warning stands on three builds. **Brave is still unmeasured** — the one client #268 names that no column covers, and an install decision rather than a command.
3. ~~**`WebMCP.invokeTool` is never exercised.**~~ ✅ **Done 2026-09-01** — `invoke-paths.mjs`. Both paths execute and return the same payload, but the shapes differ and the domain path is asynchronous, so an adapter cannot treat them as interchangeable. The parameter shape is documented nowhere this project can cite; it was walked out of the CDP deserializer's own errors, one mandatory field at a time (`frameId`, then `input` as an object, then `toolName`). Two things this unlocks: the domain path is what a real client uses, and `toolInvoked` carrying `{toolName, input}` is the mechanism the sampled Mode B design records with — see `docs/concept.md`, "Mode B, as designed on 2026-09-01".
4. **Nothing here is tested**, on purpose — a probe is a measurement, not a component. If a probe's logic ever becomes load-bearing for a published number *or for a decision*, it moves into `core/` or `browser/` and gets tests, as the manifest reader and the browser-side tool view both did — and as `cohort.mjs`, `gallery.mjs`, `scorecard.mjs` and now `visibility.mjs` did, because a one-day capture, a document sent to a stranger and a gate in front of a push are all load-bearing by definition. The runners for those four stay here; their rules do not.
5. ~~**The eight client facts these probes established are not a matrix yet**~~ ✅ **Assembled 2026-09-03** into [`reports/compatibility-matrix.md`](../reports/compatibility-matrix.md) — 22 rows, **four** build columns, every cell carrying its date and the probe that produced it. Assembling it was not transcription: `launch-probe`, `fixture-manifest`, `webmcp-domain` and `frame-scope` were all re-run that morning, and the protocol read added a row the log did not have (the browser's `Tool` type carries `frameId`, `backendNodeId` and a `stackTrace`, so **provenance exists browser-side and not page-side**). It also caught the app's silent Chromium bump, which the afternoon's re-measurement turned into the third column — and into the correction in the `chatgpt-browser-probe.mjs` row above. The evening added the Edge column (`WEBMCP_GAUGE_CHROME`, no code changes) and the two cross-site rows (`site-scope.mjs`).
